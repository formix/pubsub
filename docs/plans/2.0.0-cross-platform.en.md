# Plan 2.0.0: Linux, macOS and Windows support

> **Status:** implemented on the `2.0` branch (phases 0 to 4). Verified on Linux only: the
> macOS and Windows code paths are written but have not run on those systems yet, so the CI
> matrix (`.github/workflows/tests.yml`) is their first real test.
>
> **Differences between the plan and the implementation**
>
> - `subscribe` now runs without signal handling when it is called from a thread other than
>   the main one (installing a handler there used to raise `ValueError`); the plan's
>   exclusion tests need subscribers in threads.
> - `subscribe` restores the previous signal handlers when it ends. Before, its own
>   handler stayed installed after it returned.
> - Unchanged on purpose: after the loop ends because of a signal, `subscribe` still calls
>   the original handler. For SIGINT that is Python's `default_int_handler`, so
>   `KeyboardInterrupt` is raised after the loop has ended and the channel is closed by the
>   `with` block. SIGTERM and SIGBREAK have no callable original handler, so `subscribe`
>   returns -1.
> - Multi-process tests start their subscriber through a `multiprocessing.Event` instead of
>   a fixed sleep, because `spawn` (Windows, macOS) starts a process much slower than `fork`.
> - mypy was not part of this work; it already reported 16 errors on `main` and now reports
>   more because of the platform-specific modules (`winreg`, `ctypes` Windows APIs).
> **Target version:** 2.0.0
> **Origin:** read-only analysis of the 1.0.2 code. Nothing has been tested on Windows or
> macOS; items marked *(to verify)* need validation on a real machine or in CI.

## 1. Context and goal

`formix-pubsub` is a serverless, dependency-free inter-process pub/sub library. Messages
are stored as files, and one POSIX FIFO (`mkfifo`) per channel notifies subscribers and
orders messages.

**Goal:** make the package work on Linux, macOS and Windows with the same public API
(`Channel`, `publish`, `fetch`, `subscribe`) and no external dependency.

## 2. Diagnosis: what breaks on Windows

| # | Location | Problem | Severity |
|---|---|---|---|
| 1 | `channel.py`: `os.mkfifo` | Does not exist on Windows. Raises `AttributeError`, which the `except OSError` does not catch: `Channel(...)` crashes. | Blocking |
| 2 | `channel.py`, `pubsub.py`: `os.O_NONBLOCK` | Does not exist either. Non-blocking FIFO reads and writes are impossible. | Blocking |
| 3 | `pubsub.py`: `os.link` | Works on NTFS; unavailable on FAT/exFAT and some network shares. | Medium |
| 4 | `pubsub.py`: signals | SIGTERM is never delivered on Windows (a kill is a hard `TerminateProcess`). Only Ctrl+C (SIGINT) and Ctrl+Break (`SIGBREAK`) arrive. | Medium |
| 5 | `abstractions.py`: `is_process_running` | `OpenProcess` fails with `ACCESS_DENIED` for another user's or an elevated process, which then looks dead: `cleanup_inactive` could delete a live channel. Same risk on POSIX with `PermissionError`. | Medium |
| 6 | Deleting open files | Windows refuses to delete an open file without `FILE_SHARE_DELETE`. The publisher's `unlink` of the tmp file can raise `PermissionError` while a subscriber reads the same inode. *(to verify)* | Medium |
| 7 | `abstractions.py`: base dir | No `/dev/shm`. Falls back to `%TEMP%` (on disk, per user). | Low |
| 8 | Outside the package | `scripts/*.sh`, `deploy.sh`, tests and documentation that mention "kernel FIFO" and `/dev/shm`. | Low |

**Central finding:** the FIFO no longer carries data, only the message id (8 bytes). The
content is already in a file linked into the channel directory. The FIFO only provides
notification, ordering, and "channel is open" detection (`ENXIO`). Items 1 and 2 are
therefore the real problem; the others can be fixed afterwards.

## 3. Decisions made

| # | Decision |
|---|---|
| **D1** | **The FIFO is removed everywhere** (no per-platform backend). One code path, testable on all three OSes. |
| **D2** | **Channel lifecycle.** `Channel(topic)` performs no I/O. `open()` creates the directory; the directory's existence means "channel is open" (replaces `ENXIO`). `close()` renames the directory to `base/purge/<token>_<channel>`, then deletes its contents, then the directory. No `queue` marker. |
| **D3** | **`fetch`.** A cache of sorted message file names (zero-padded, D13) is filled by `scandir` only when it is empty. It is cleared on `open()` and `close()`. A vanished file (`FileNotFoundError`) is skipped. |
| **D4** | **`publish`.** `os.link` from the tmp file to `<channel>/<id>` is the atomic commit point; nothing is written to a FIFO anymore. Id collision detection (`FileExistsError`) is kept. |
| **D5** | **`subscribe`.** Waiting goes through a native `DirWatcher` (inotify, kqueue, `FindFirstChangeNotification`) with an adaptive polling fallback. A notification is a hint: the directory is always rescanned. |
| **D6** | **No `sleep` after a message is received** (removes the current ~100 msg/s ceiling). |
| **D7** | **Version 2.0.0.** This is a major version. `Channel.queue_path` (a public attribute) and `_fp` go away, `Channel` no longer creates its directory before `open()`, and the transport changes (no FIFO, zero-padded file names), so processes running 1.x and 2.0 can no longer exchange messages. All of it must be called out in the release notes. |
| **D8** | **One `subscribe` per channel.** A channel cannot be shared between several consumers through `subscribe`. A second `subscribe` call on a channel that is already being listened to raises a `RuntimeError`. |
| **D9** | **`fetch` is forbidden on a channel being listened to.** A direct `fetch` call on a channel with an active `subscribe` raises a `RuntimeError`, including when called from that `subscribe`'s own callback. |
| **D10** | **No strict ordering between concurrent publishes.** Whatever is linked into the channel first is delivered first, even if its id is larger than that of a message still being written (e.g. a slow, large message that started earlier). Ids are a deterministic tie-breaker, not an ordering promise. Messages published sequentially by one publisher (each `publish` returning before the next starts) are always delivered in that order. |
| **D11** | **Windows path length is checked, not capped.** `Channel(topic)` raises an `OSError` (`errno.ENAMETOOLONG`) on Windows when the longest path it will create reaches the `MAX_PATH` limit and Windows long paths are not enabled. The message explains how to remove the Windows path length limitation (see 4.6). No fixed topic-length cap is imposed. |
| **D12** | **Stale temporary messages are swept.** `Channel.cleanup_inactive()` also deletes the files of `tmp/` that are older than one hour, the age being read from the message id. This removes the files left by a publisher that was killed between writing its temporary file and deleting it. |
| **D13** | **Message file names are zero-padded.** Every message file name (in `tmp/`, in channel directories, and in the `.part` fallback) is the message id formatted as exactly 20 digits, left-padded with `0` (`f"{id:020d}"`, 20 being the length of the largest 64-bit id). Plain string order then equals numeric order, whatever the platform or file system. A single helper in `message.py` builds and parses these names. |
| **D14** | **Manual acknowledgement.** `fetch(channel, auto_ack=True)` and `subscribe(..., auto_ack=True)` take an `auto_ack` parameter. With `auto_ack=False` the message stays locked (`<id>.locked`) and the caller disposes of it with `ack(channel, message)` (delete it) or `nack(channel, message)` (rename it back to `<id>`, so a later `fetch` or `subscribe` delivers it again). Once a message has been handed out, the channel keeps no record of it: `ack` and `nack` act on the file alone. A nacked message is delivered by the first directory listing that happens after the messages already listed have been delivered. With `subscribe(auto_ack=False)` the callback calls `ack` or `nack`; a message left alone, or whose callback raised, stays locked until the channel is closed. |
| **D15** | **Poison messages.** `nack(channel, message, poison=False)`. With `poison=True` the message is moved to the `poison` sub-directory of the channel (`Channel.poison_path`, created on first use) under its original name, and is never delivered again by this channel: it is left to whoever handles the poison messages, to avoid reprocessing a message that always fails. Every `nack` is logged, at INFO level when the message goes back to the channel and at WARNING level when it is moved as poison, even if the message file is already gone. The poison folder is deleted with the channel when it is closed. |

## 4. Detailed design

### 4.1 On-disk layout

```
base/
├── tmp/<id>                                  publisher scratch (files only)
├── purge/<token>_<channel>                   closed channels being deleted
└── <topic>_<rand12>_<pid>/                   open channels
    └── <id>                                  message files (name = id padded to 20 digits)
```

- `active_paths` and `inactive_paths` already ignore `tmp`: its name has fewer than three
  `_`-separated segments. `purge` is in the same situation, and a channel name always
  contains at least two `_`, so no name collision is possible. These functions do not
  need to change.
- `base` is `PUBSUB_HOME` if set, otherwise `/dev/shm/pubsub` (Linux) or
  `<tempdir>/pubsub` (macOS, Windows).
- `<id>` in every file name of this plan stands for the zero-padded 20-digit form (D13).
### 4.2 `Channel`

| Call | Effect |
|---|---|
| `Channel(topic)` | Validates the topic, computes `random_id`, `directory_name`, `directory_path`, and on Windows checks the path length (D11). No file-system I/O. |
| `open()` | `mkdir(parents=True)` on the base, `mkdir(exist_ok=False)` on the channel directory. Cache cleared, `_open = True`. Idempotent if already open. |
| `close()` | No-op if never opened. Otherwise: see below. |

`close()`:

1. Close the watcher, clear the cache, `_open = False`. *On Windows, a notification handle
   on the directory may block its rename: do this first. (to verify)*
2. `purge.mkdir(exist_ok=True)`.
3. `os.rename(base/<channel>, base/purge/<token>_<channel>)` with `_retry`. Atomic: same
   volume.
4. Delete the contents (`_delete_recursive`, with `_retry`), then the directory.
5. If the rename still fails after retries (Windows: antivirus, indexer), delete in place.
   The directory stays briefly visible to publishers: acceptable.

Details:

- **`token`**: 8 random alphanumeric characters, as a **prefix**, so `parts[-1]` remains
  the PID as everywhere else in the code. It avoids a conflict if the same channel is
  closed and reopened while an earlier purge is still running.
- This fixes an existing leak: today, `close()` on a channel that was never opened returns
  without deleting anything.
- A `publish` that had already resolved the old path gets `FileNotFoundError` on `link`:
  it skips the channel without counting it. A `link` that succeeds just before the rename
  is deleted with the rest (message delivered but lost, as with the FIFO today).

### 4.3 `publish`

- Writing the tmp file is unchanged (`open(..., "xb")`, collision detected).
- For each active matching channel: `os.link(tmp, channel/<id>)`, then count. No more
  `queue.exists()` check, no FIFO write, no `struct.pack`.
- `FileNotFoundError` on `link`: normal race (channel closed meanwhile), `debug` log.
  Other `OSError`s remain a warning. `FileExistsError` remains an id collision.
- The tmp `unlink` uses `_retry` on `PermissionError`.
- **Fallback without hardlinks** (FAT/exFAT, shares): detected once, when the first `link`
  fails, and remembered. Copy to `channel/.<id>.part`, then `os.rename` to
  `channel/<id>` (on Windows `rename` fails if the target exists, which preserves
  collision detection; on POSIX, a prior existence check, not atomic).

### 4.4 `fetch`

```text
if channel is not open: RuntimeError
if cache is empty:
    cache = sorted((e.name for e in scandir(dir) if is_message_name(e.name)),
                   reverse=True)      # descending names
while cache is not empty:
    name = cache.pop()                # smallest id
    open/read the file, Message.read   (FileNotFoundError -> next)
    unlink (with _retry), return the message
return None
```

- File names are zero-padded to 20 digits (D13), so sorting the names as strings gives
  numeric id order. No integer conversion is needed when listing.
- `is_message_name(name)` is true only for exactly 20 digits. It ignores the fallback's
  `.part` files and anything else that does not follow the naming.
- A backlog of n messages costs one listing plus one sort, not n listings.
- No more loss window (today, an id read from the FIFO whose file has vanished is lost).

### 4.5 `subscribe` and `DirWatcher`

Internal interface: `DirWatcher(path)` with `wait(timeout)` and `close()`, selected by
`sys.platform`.

| OS | Implementation | Notes |
|---|---|---|
| Linux | **inotify** via `ctypes`, `IN_CREATE` and `IN_MOVED_TO` | **One instance shared per process** (`fs.inotify.max_user_instances` defaults to 128), one watch per channel (a `wd → channel` table). Usable with `select`. Reliable on tmpfs and ext4; not on WSL2's `/mnt/c`, NFS or SMB. A `link()` generates `IN_CREATE`, and the file is already complete at that point. |
| macOS / BSD | **`select.kqueue`**, `EVFILT_VNODE` + `NOTE_WRITE` on a descriptor of the directory | In the stdlib. One descriptor per channel. Does not say which file changed: irrelevant since we rescan. *(to verify on macOS)* |
| Windows | **`FindFirstChangeNotification`** / `FindNextChangeNotification` via `ctypes`, waited on with `WaitForSingleObject` | The handle is not usable with `select`. `ReadDirectoryChangesW` adds nothing here (it would report the file name). |
| Fallback | **Adaptive polling**: 0, then 1, 2, 5, 10, 25 and up to ~50 ms when idle; back to 0 as soon as a message arrives | When the watcher is unavailable (limit reached, silent file system, `ctypes` unavailable). |

Common rules:

1. **Notification is not data**: after every wake-up or timeout, rescan. Lost or coalesced
   events (inotify overflow) are recovered this way.
2. **Subscribe before the first scan**, so a message arriving between the two is not missed.
3. **Every wait is interruptible by a signal**: duration bounded to `min(remaining,
   ~100 ms)`, or `signal.set_wakeup_fd` for an immediate stop. `WaitForSingleObject` is
   not interrupted by Ctrl+C; on POSIX, `select` resumes after a handler that does not
   raise (PEP 475).
4. `timeout_seconds` is still honored.
5. No `sleep` after a message is received (D6).
6. **Signals**: register `SIGBREAK` on Windows; document that SIGTERM has no effect there.
7. **Only one active `subscribe` per channel (D8).** The channel carries a subscription
   flag, protected by a lock. `subscribe` sets it on entry and raises `RuntimeError` if it
   is already set; it clears it in its `finally`, whatever the exit (timeout, signal,
   exception). The channel's id cache is not designed for several consumers: forbidding
   them avoids duplicate reads without a per-message claim mechanism (atomic rename).

   **Exclusion mechanism (D8 and D9).** The `Channel` owns all of the state: its list of
   pending message files, a subscription flag, and the lock that protects them. Code outside
   the class never touches them; it uses the channel's public methods:
   - `begin_subscription()` / `end_subscription()` / `is_subscribed`: `subscribe` registers
     as the channel's single listener (a second one gets `RuntimeError`) and unregisters in
     its `finally`.
   - `begin_read_message(subscribed=False)` / `end_read_message(message)` / `cancel_read_message(message)`: the channel owns
     the files inside its directory. `begin_read_message` lists the directory when the
     pending list is empty (loading is the channel's own business), then **claims** the next
     file, in id order, by renaming it `<id>.locked` (`LOCKED_SUFFIX`), reads it and returns
     the message. The rename is atomic, so a given message is handed to one reader only; a
     file that vanished or was claimed first by someone else is skipped. A locked name is no
     longer a message file name, so no listing hands it out again, and the channel keeps no
     in-memory record of the files being read. `end_read_message` deletes the locked file:
     `subscribe` calls it after the callback (also when the callback raises) and `fetch`
     calls it at once. A file that is not a valid message stays locked in the channel and is
     never handed out again; locked files are deleted when the channel closes.
     With `subscribed=False` (direct `fetch`) `begin_read_message` raises `RuntimeError`
     while a subscribe is registered; with `subscribed=True` (the subscribe loop) it
     requires a registered subscription.
   - Known limitation: once a message is claimed, its original name is free again, so a
     publisher that produced the very same id (same millisecond, same low 10 bits of the
     PID, same sequence number) would no longer hit the collision check for that channel.
     This was already astronomically unlikely and is accepted.
   - Check and hand-out happen under the channel's lock, so there is no race with a
     `subscribe` starting, and two threads calling `fetch` get different files.
   - The lock is released before the file is read and before the callback runs, so a `fetch`
     called from a callback raises instead of deadlocking. Document it as forbidden.

### 4.6 Windows and general support

- **`is_process_running`**: `PROCESS_QUERY_LIMITED_INFORMATION`, `GetExitCodeProcess`
  compared with `STILL_ACTIVE` (259), and `ERROR_ACCESS_DENIED` interpreted as "alive".
  On POSIX, `PermissionError` also means "alive".- **`_retry(fn, attempts≈5, delay≈5 ms)`** for `unlink`, `rmdir` and `rename` on
  `PermissionError` (open file, antivirus, indexer).
- **Path length (D11).** On Windows, without long-path support, a path is limited to 259
  characters (`MAX_PATH` is 260, including the terminating null).
  - *What is checked.* The longest path pubsub will create:
    `<base>\purge\<token>_<directory_name>\<entry>`, i.e. `len(base) + len("\purge\") + 9 +
    len(directory_name) + 1 + 27` (token 8 characters plus `_`; the longest entry of a
    channel is a locked message `<id>.locked` or a poison message `poison\<id>`, both 27
    characters, D13). It is the path of such an entry inside a channel being purged, which
    is longer than any other path pubsub creates. It is a pure computation, done in
    `Channel.__init__` with no file-system I/O.
  - *When it fails.* If that length reaches 260 characters and long paths are not enabled,
    `Channel(topic)` raises `OSError(errno.ENAMETOOLONG, message)`. `PUBSUB_HOME` is part
    of the computation, so a long `PUBSUB_HOME` is reported too. Nothing is created on disk.
  - *Is it enabled?* `windows_long_paths_enabled()` in `abstractions.py` reads
    `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled` with `winreg`
    (stdlib), cached. A value of `1` skips the check; an unreadable value counts as
    "disabled". Python 3.11 and later declare themselves long-path aware, so no other
    setting is needed in the interpreter.
  - *The message* states the computed length and the limit, then suggests: shorten the
    topic or set a shorter `PUBSUB_HOME`; or remove the Windows path length limitation,
    either by re-running the Python installer (Modify) and ticking **Disable path length
    limit** on the last screen, or by setting the `LongPathsEnabled` registry value above
    to `1` (administrator rights, Windows 10 version 1607 or later); then restart the
    application.
  - *Also translated:* if the OS reports `ERROR_FILENAME_EXCED_RANGE` (206) from `mkdir`,
    `rename` or `link` anyway, it is raised with the same explanation.
  - *Not checked on Linux and macOS:* their path limits (4096) are far above what pubsub
    needs.
- **Permissions**: the FIFO's `chmod 660` no longer applies. For POSIX multi-user use, the
  `mkdir` mode is what matters; on Windows, the ACLs inherited from `PUBSUB_HOME`.
- **Reserved names** (`CON`, `NUL`…): no risk, a channel name always ends with
  `_<rand12>_<pid>`. The `=` and `+` characters are valid in NTFS names.
- **Cleanup**: `cleanup_inactive` also covers `purge/` (see 4.2). `_delete_recursive` must
  tolerate `FileNotFoundError` along the way (several cleaners may cross paths).
- **Stale message sweep (D12).** `cleanup_inactive` also scans `tmp/` with `os.scandir`:
  - Only entries whose name is a message file name (exactly 20 digits, D13) are
    considered. Anything else is left alone.
  - The age comes from the id: the upper 42 bits are milliseconds since the epoch, so
    `ms = id >> 22` (10 process bits + 12 sequence bits). No `stat` call is needed.
  - An entry older than `STALE_TMP_SECONDS` (one hour, a module constant) is deleted with
    `unlink`. One hour is far longer than any normal write of a temporary file, which keeps
    a live publisher's file safe even if the system clock moves.
  - `FileNotFoundError` (another cleaner or the publisher got there first) is ignored.
    `PermissionError` on Windows (the file is still open) is logged at debug level and left
    for the next sweep.
  - Hardlinks already placed in channel directories are separate names for the same data
    and are not affected: a message that reached some channels before its publisher died
    stays deliverable there.
  - Like the rest of `cleanup_inactive`, it runs only when the function is called.

### 4.7 Semantics compared with 1.0.2

| Aspect | 1.0.2 (FIFO) | 2.0.0 (spool) |
|---|---|---|
| Delivery order | Arrival order in the FIFO | Increasing id order (≈ chronological) |
| Late message | Impossible | Accepted (D10): a slow publisher can link a smaller id after a larger id was delivered; it is delivered in the next batch. Messages linked between two scans are delivered in id order, which may differ from link order |
| One publisher, one thread | Order guaranteed | Order guaranteed |
| Message loss | Possible if the file vanished after the id was read | Window removed |
| Message published before `open()` | Not delivered (`ENXIO`) | Not delivered (no directory) |
| Channel never opened | Directory left on disk | No directory created |
| Latency | 10 ms poll | Native event, polling fallback |
| Backlog | O(1) per message | O(n) listing and O(n log n) sort per batch |

## 6. Implementation phases

### Phase 0: safety net

- CI with `ubuntu-latest`, `macos-latest` and `windows-latest` (Python 3.11 to 3.14). It
  will fail on Windows at first: that is the starting baseline.
- Move the nested `subscriber_process` functions of `tests/test_pubsub.py` to module
  level: on Windows, `multiprocessing` uses `spawn` and cannot pickle them.
- Raise the `timeout=1` of the `result_queue.get(...)` calls (slower `spawn` startup).
- Review or skip on Windows the tests that send `SIGTERM`. *(to verify)*

### Phase 1: spool core (works everywhere, with polling)

0. `message.py`: D13. Add the helper that builds a message file name from an id
   (`f"{id:020d}"`), parses it back, and tells whether a name is a message file name
   (`is_message_name`). Every place that currently uses `str(message.id)` goes through it.
1. `channel.py`: D2. Remove `mkfifo`, `chmod`, `os.open/os.close`, `_fp` (replaced by
   `_open: bool`) and `queue_path`. `close()` with rename to `purge/`.
2. `pubsub.py`, `publish`: D4 and the no-hardlink fallback.
3. `pubsub.py`, `fetch`: D3 and D9 (`Channel.begin_read_message`, `end_read_message`, `begin_subscription`,
   `end_subscription`).
4. `pubsub.py`, `subscribe`: D6, D8 (one `subscribe` per channel), with provisional adaptive-polling wait.
5. Adapt the tests (see section 8).

*End of phase:* all three OSes work. Windows hardening and latency remain.

### Phase 2: Windows and general hardening

- Fixed `is_process_running` (4.6).
- `_retry` helper, used for the publisher's tmp file, `_delete_recursive`, `close()` and
  the rename.
- `cleanup_inactive` covers `purge/`; `_delete_recursive` tolerates races.
- Signals: `SIGBREAK`, README corrected.
- Windows path-length check (D11): `windows_long_paths_enabled()` helper and the check in
  `Channel.__init__`.
- Stale `tmp/` sweep in `cleanup_inactive` (D12).

### Phase 3: native wake-up (`DirWatcher`)

Implementations from 4.5: inotify (shared instance), kqueue, `FindFirstChangeNotification`,
and the fallback. An environment variable or internal parameter forces the polling
fallback so that path can be tested in CI.

### Phase 4: documentation and release

- README and docs: "kernel FIFO" and `/dev/shm` become "files in a directory with
  file-system notification". Document `PUBSUB_HOME` (Windows: `%TEMP%` by default, per
  user), NTFS required or fallback, `SIGBREAK`, path limits.
- `.ps1` equivalents (or documented commands) for `scripts/*.sh` and `deploy.sh`.
- `pyproject.toml`: version 2.0.0, `Operating System ::` classifiers.
- Release notes: removal of `queue_path`, transport incompatibility between 1.x and
  2.0.0 (an old subscriber and a new publisher no longer see each other, and vice versa).

- An unpadded numeric name in a channel directory or in `tmp/` is ignored by `fetch` and by
  the sweep.
- Manual acknowledgement (D14): `fetch(auto_ack=False)` leaves the file locked; `ack`
  deletes it; `nack` gives it back under its own name and it is delivered again, after the
  messages already listed; `ack` and `nack` twice or after the channel closed do nothing; a
  message never disposed of is deleted with the channel; `subscribe(auto_ack=False)` leaves
  disposal to the callback, including when the callback raises.
- Poison messages (D15): `nack(poison=True)` moves the file to `poison/<id>`, creating the
  folder on first use; the message is never delivered again; its content is readable;
  other messages are unaffected; the folder is deleted with the channel; twice or after
  close is harmless and does not recreate the folder; a failed move is logged and leaves
  the message locked; the callback of `subscribe` can send a message to the folder. Every
  `nack` is logged (INFO, or WARNING for poison), also when the message is already gone.
- Late message (small id linked after a larger one) delivered in a later batch, without
  loss; no cross-publisher order is asserted.
- Messages published sequentially by one publisher are delivered in publication order.
- Messages published before `open()`: not delivered.
- File vanishing between listing and reading: skipped.
- Fallback without `os.link`.
- `close()`: `purge/` keeps nothing of that channel; `close()` followed immediately by
  `open()` yields a clean channel.
- `active_paths` and `inactive_paths` ignore `purge/`.
- `cleanup_inactive`: a `purge/` entry for a dead PID is removed, one for a live PID is
  left alone.
- `_retry` on `PermissionError` (with an injected failure).
- Stale `tmp/` sweep (D12), with an injectable clock:
  - a file whose id is older than one hour is removed by `cleanup_inactive`, a recent one
    is kept;
  - an entry of `tmp/` that is not a 20-digit message file name is never touched;
  - a vanished file during the sweep is ignored;
  - `PermissionError` on a stale file does not abort the sweep;
  - the age is computed from `id >> 22` and matches the ids produced by `Message`.
- Windows path length (D11), with injectable platform and long-path settings so it runs on
  every OS:
  - a path of 259 characters is accepted, 260 raises `OSError` with `ENAMETOOLONG`;
  - the computed length includes `PUBSUB_HOME`, the `purge` folder, the purge token, and a
    20-digit id;
  - long paths enabled → no error for the same inputs;
  - registry value unreadable → treated as disabled;
  - the message contains the computed length, the limit, and the long-path instructions;
  - an OS-reported error 206 is raised with the same explanation;
  - on Linux and macOS no check is applied.- Each `DirWatcher`: fast wake-up on message arrival, and forced polling fallback.
- Signal shutdown: SIGINT everywhere, `SIGBREAK` on Windows.
- A second `subscribe` on a channel that is already being listened to (from another
  thread): `RuntimeError`; after the first `subscribe` ends (timeout, signal or
  exception), a new `subscribe` on the same channel is accepted again.
- `fetch` on a channel with an active `subscribe`: `RuntimeError`, both from another
  thread and from the `subscribe` callback itself (no deadlock); after `subscribe` ends,
  `fetch` works again.
- Two threads calling `fetch` concurrently on a channel with no `subscribe`: no error,
  each message delivered once.

## 9. Risks

| Risk | Mitigation |
|---|---|
| Ordering change (D10) | Document that there is no cross-publisher ordering guarantee; test per-publisher order |
| Unverified Windows behavior (tmp-delete race, handle blocking the rename, `FindFirstChangeNotification`) | `windows-latest` CI from phase 0; `_retry`; delete-in-place fallback |
| `NOTE_WRITE` on a directory on macOS | Validate in macOS CI; polling fallback |
| System limits (inotify `max_user_instances`, descriptors for kqueue) | Shared inotify instance; polling fallback |
| `/mnt/c` (WSL2), NFS, SMB: unreliable events | Timeout ceiling and rescan; documented polling fallback |
| Transport incompatibility between 1.x and 2.0.0 | Major version number; explicit release notes |
| Windows antivirus / indexer briefly locking files | `_retry` |
## 10. Acceptance criteria

- The test suite passes on `ubuntu-latest`, `macos-latest` and `windows-latest`.
- A publisher and a subscriber in two separate processes exchange messages on all three
  OSes.
- Per-message latency with the native watcher is well below 10 ms; the polling fallback
  works everywhere.
- A subscriber shuts down gracefully on Ctrl+C on all three OSes.
- No channel directory leaks after `close()`, including for a channel that was never
  opened.

## 11. Rejected alternatives

| Option | Reason |
|---|---|
| **WSL2 only** | No code change, but native Windows processes cannot talk to WSL ones. Not real Windows support. |
| **Windows named pipes** (`CreateNamedPipe`) | Semantics close to a FIFO but heavy: multiple instances, overlapped I/O, disconnects. High complexity. |
| **Windows mailslots** | Close to a FIFO and usable through `ctypes`, but an old, poorly documented API and one more backend to maintain. |
| **Loopback sockets** (UDP/TCP) | Portable, but firewall prompts, port management, datagram loss with UDP. More moving parts than the spool. |
| **Keep a FIFO backend on POSIX** | Two code paths; the FIFO no longer carries data (D1). |
| **`watchdog`** (third party) | Wraps all four mechanisms, but adds a dependency and an observer thread. Could become an optional extra later. |
| **Reuse `tmp/` for the purge** | Would mix message files and channel directories in one folder, with orphan cleanup having to tell them apart; `purge/` is clearer. |
